Part 2

Release Flow

Release nomenclature and the eighteen steps every release passes through. Each step is tagged with the day on the timeline above when it happens. After merge, the test cases and release notes are created, the internal snapshot is cut, and both are reviewed before main testing. Four points in the flow can send work back.

Release nomenclature

Decided
26Year . 2Major . 3Minor . 1Hotfix

Read 26.2.3.1 as: the 2nd major release line cut in 2026, its 3rd minor release, and the 1st hotfix on top of that minor. A normal release stops at three numbers: 26.2.3. The fourth number appears only on a hotfix.

The eighteen steps

4 decision points
01

Discussion PM days 1–6, release before

  • This is a guideline, not a gate: the PM must be clear on the work before writing the ticket.
  • Clarity is shared across PM, dev and ML team. Open questions get resolved first.
  • R&D and discussion happen while the PRD is being written. Sagar books the sessions and attends every one. Dev–PM discussions are kept to a minimum.
  • On day −3 (day 7 of the previous release), the morning Product Sync covers the gists: Vaibhav explains each PRD to Akshat and Sagar, and Akshat gives the gist of the enhancement whitepapers.
02

Ticket creation Sagar Claude · Skill · ticket-creation days −3 to −1

  • Sagar starts ticket creation on day −3, continues on day −2 and closes it on day −1 (days 7–9 of the previous release), the deadline. All planning discussions with devs close on day −1 too. The PM doesn't create tickets.
  • Every ticket is written clearly enough that no dev discussion is needed.
  • Each ticket has a business use-case, and executionals written as user stories with acceptance criteria against each.
  • Every ticket carries the fix version, added once release planning (03) decides the release version.
  • Each ticket's release-note text is drafted here, along with placeholders naming the screens the notes will need images of.
  • Also recorded: whether migration is needed and its type(s), prototype links, creator, component, sub-component and assignee.
03

Release planning Sagar days −3 to 0

  • This happens on days −3 to 0, which are days 7–10 of the release before. Sagar assigns tickets by bandwidth and locks the list on day −1: Commit Items that must ship, and Buffer Items for when a dev is free.
  • The list is locked on day −1. On day 0, the Product Sync reviews it, adds items as needed, and decides whether the release is major or minor, which sets its version using the nomenclature above.
  • Scope is the set of tickets that will carry this version as their fix version.
04

Development Dev days 1–7

  • Devs build the executionals in the ticket and write test cases on the ticket.
  • A migration script is maintained where migration is required. Upgrades run one version at a time until the latest version is reached.
05

PR created Dev days 1–7

  • One PR per ticket.
06

PR vetting Claude · Skill days 6–7

  • Claude reads the Jira ticket and the code, vetting the PR against the dev's test cases and the PM's ticket description.
  • Checks for migration gaps and for gaps between Jira and the code.
  • R&D and discussion tickets have no PR and are skipped.
07

Vetting report Ticket's dev vets Claude · Skill Decision point days 6–7

  • Claude creates a report for each PR, and the dev who owns the ticket vets it. The PM is brought in only when something is urgent.
  • NOK → back to development (04). OK → proceed to merge.
08

Merge Dev days 6–7

  • The ticket's PR is merged once the vetting report is OK.
09

Test cases + release notes created Claude · Skill day 7

  • Test cases created. Claude generates release-level test cases from the tickets carrying this fix version.
  • Release notes created. Claude drafts the notes from the ticket note text written at step 02, with the image placeholders left in. R&D and discussion tickets are left out.
10

Internal release snapshot Release dev day 7 EOD

  • Code freezes at the end of day 7. The release dev cuts the release branch and the snapshot is taken from it. Everything that follows runs against this one snapshot.
  • On day 8, the release dev reviews the overall PR merge report.
11

Test cases + release notes reviewed PM Decision point days 8–9

  • Test cases reviewed PM · day 8. NOK → the PM tweaks the set by prompt and it is reviewed again. No ticket or code change is involved. OK → main testing starts.
  • Release notes reviewed PM, Akshat, Sagar · day 9. Vaibhav, Akshat and Sagar read the draft out in the day 9 Product Sync. Gaps are fixed by prompt, and the draft then waits for the test result.
12

Main testing + screenshots Triggered by the release dev Claude · Skill days 8–9

  • Once the test cases are reviewed, the release dev triggers Claude main testing on the snapshot.
  • The release-note screenshots are captured during this run, not in a separate pass afterwards. The run is already on each of those screens, in the required state, on this snapshot.
  • The captured images are kept with the run. If the report is approved, the images come from the approved snapshot. If it is not, they are discarded with that snapshot.
13

Test report generated Claude · Skill day 9

  • Main testing produces a testing report.
14

Test report reviewed Release dev Decision point day 9

  • OK → testing is done and the release notes can be finalised (16).
  • NOK → the gaps are shown, and the call is made at 15.
15

Halt or ship decision PM + Dev Claude · Skill days 9–10

  • Halt the release → back to development (04) for fixes. The fixes come back through the same flow and are retested on a new snapshot. The release dev owns fixes and retests, and the PM oversees them.
  • Ship with the bugs as known issues → the screenshots already captured go to step 16.
  • Bugs are created automatically at this step, whichever way the call goes.
16

Release notes finalised PM reviews Claude · Skill Decision point day 10

  • Runs once the test report is OK (14), or once the decision is to ship with known issues (15).
  • The draft reviewed at 11 takes the screenshots from main testing (12) and any known-issue bugs (15), and the PM makes the final tweaks.
  • NOK → prompt-based tweaks only: wording, ordering, or swapping an image. The test report is already approved at this point, so nothing here goes back to a ticket or to code.
  • OK → publish.
17

Release, files and notes published PM + release dev day 10 EOD

  • Vaibhav and Swayam send the release on day 10 by EOD. Deb covers when Swayam is out. If it slips to day 11, they finish it while Sagar starts the next release.
  • Three things go out together: the release, the release files (the scripts bundle for the installer) and the release notes.
  • When scripts are updated at the installer, a DB backup is taken. It covers a release that goes bad and is the restore point for a rollback.
  • Plants update on their own schedule. Updating the bundle requires pulling the matching instance version from Vision.
18

Manuals updated PM reviews Claude · Skill after the release

  • A separate skill updates the manuals once the release is out.
  • The source is the ticket executionals, so manuals and release notes describe the same change.

Hotfix releases

Panic path

A hotfix is a panic release shipped within 1–2 days, with minimal discussion, a ticket and a quick fix.

  • Such tickets carry a hotfix tag.
  • Ticket type can be Story or Bug.
  • The version takes a fourth number on top of the current minor: 26.2.3 → 26.2.3.1, then 26.2.3.2 and so on. Nothing else carries a fourth number.

Decisions still needed

  • Re-vetting after a NOK at 07: does the corrected PR go back through vetting, or is the release dev's sign-off enough the second time?
  • Migration testing against old data: PR vetting confirms the migration code exists, but nothing yet confirms it works. The release-level test cases at step 09 are the natural place for it.
  • Four-part version tooling check: roughly an hour for a dev to confirm that package.json, image tags, installer sort order and version-comparison libraries all accept four parts.

Coding guidelines

One ticket, one merge
  • Every ticket must have something merged against it. A ticket closed with no merge behind it can't be traced.
  • Work belonging to several tickets must not be merged under one ticket. Each ticket's changes go in that ticket's own PR.

The rest of the process depends on this. PR vetting at step 06 compares one ticket against one diff. If a PR carries three tickets' worth of work, there is no single description to check it against, and vetting can't say whether the code matches the ticket. The same problem carries downstream: release notes and manuals are generated per ticket, so work merged under the wrong ticket is described as the wrong change, or not described at all.

It also keeps the fix version honest. Release scope is a Jira query on the fix version, so a ticket carrying hidden extra work makes the release larger than the query shows.
